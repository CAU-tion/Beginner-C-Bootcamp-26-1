1. 오프셋(Offset) 계산

목표: 스택에 저장된 Return Address(복귀 주소, RET)를 덮어쓰는 것 
-> RET에 도달하기 전까지 덮어써야 하는 쓰레기 데이터의 크기가 오프셋

메모리 구조 분석: C 코드에서 char buf[16] 선언 -> 어셈블리(GDB)에서 sub $0x10, %rsp를 통해 버퍼로 16바이트(0x10)가 할당된 것 확인 -> 스택 구조는 [버퍼(16바이트)] + [SFP(8바이트)] + [RET(8바이트)] 순서로 쌓여있음 (64비트 기준 SFP는 8바이트)

계산: RET 직전까지 도달하려면 버퍼(16)와 직전 함수 베이스 포인터 SFP(8)를 가득 채워야 함
결론: 16 + 8 = 24바이트. 즉, 24바이트의 더미(A*24)를 넣어 다음 차례부터 RET 주소 조작 가능

2. secret() 함수 주소 확인

목표: 덮어쓸 타겟인 secret 함수의 실제 메모리 주소 확인

확인 방법: GDB 디버거 안에서 p secret (print secret) 명령어 사용

결과: $1 = {void ()} 0x401156 <secret>

결론: 점프해야 할 최종 목적지 주소는 0x401156

3. 리틀 엔디안(Little Endian)과 주소 뒤집기

알아낸 주소를 페이로드에 입력할 때는 순서를 반대로 뒤집어서 넣어야 함 -> 리틀 엔디안 때문

리틀 엔디안: 인텔/AMD CPU(x86-64 아키텍처)가 메모리에 데이터를 저장하는 방식으로 가장 작은 단위의 바이트(LSB)부터 가장 낮은 메모리 주소에 저장
ex -> 0x401156은 전체 64비트 주소로 보면 0x 00 00 00 00 00 40 11 56

우리가 읽을 때는 왼쪽(00)이 크고 오른쪽(56)이 작은 값이지만, 메모리에는 작은 값부터 들어감

결론: (\x56\x11\x40\x00\x00\x00\x00\x00)

4. ret 가젯과 스택 정렬(Stack Alignment)

발생한 문제: 과제에서 주어진 순서대로 진행하였는데, "secret function called!"이 출력되지 않고 세그폴트 발생

문제 원인: 64비트 리눅스에서 printf 같은 특정 함수를 쓰려면 스택 포인터가 무조건 16바이트(16의 배수) 단위로 정렬되어 있어야 하기에 RET를 덮어써서 함수로 강제 점프하면, 정상적인 호출(call)로 인식하지 않아 스택이 8바이트 어긋난 채로 진입하여 크래시(세그폴트) 발생
-> call 명령어를 실행하면 CPU는 나중에 돌아올 주소(8바이트)를 스택에 push하고 점프하여 스택을 8바이트 어긋나게 만들고 이렇게 스택이 어긋나 있어야 C 표준 라이브러리(libc) 함수들 수행 가능

해결 방법 (ret 가젯): * vuln 함수 끝에 있는 ret 명령어의 주소(0x40118f)를 중간에 삽입
-> 페이로드에 [더미 24바이트] + [ret 가젯] + [secret 주소] 순으로 작성하여 문제 해결

결론: 타겟 함수로 가기 전에 의미 없는 ret 명령어를 한 번 더 실행함으로써, 스택을 8바이트 더 이동시켜 총 16바이트 정렬을 완벽하게 맞추고 secret 함수로 진입 가능하게 만듦

challenge-02

checksec 으로 확인할 수 있는 정보

1. Arch: amd64-64-little
의미: 이 프로그램은 64비트 아키텍처(amd64) 기반이며, 리틀 엔디안(little-endian) 방식으로 메모리를 저장
-> secret 함수의 주소(0x401156)를 페이로드에 넣을 때 바이트를 뒤집어서(\x56\x11\x40...)넣어야 했던 이유

2. RELRO: Partial RELRO
의미: RELRO(Relocation Read-Only)는 메모리의 특정 데이터 영역(GOT 등)을 덮어쓰지 못하게 하는 방어 기법
-> 예시 사진에서는 Partial로 적용되어 있어, 원한다면 특정 라이브러리 함수의 주소를 조작하는 'GOT Overwrite' 공격 기법 사용 가능 상태

3. Stack: No canary found
의미: 스택 오버플로우를 막는 핵심 방어막인 스택 카나리(Stack Canary) 작동 유무
-> -fno-stack-protector 옵션을 주고 컴파일하여 예시 상태에서는 No canary found로 명시되어있고, 카나리가 없었기 때문에 24바이트 더미 데이터로 스택을 덮어써서 Return Address를 조작 가능 하였음. 
만약 Canary found였다면 공격 시도 즉시 프로그램이 차단

4. NX: NX enabled
의미: NX(Non-Executable)는 메모리의 스택이나 힙 영역에 있는 데이터를 '실행'하지 못하게 막는 기법
-> 예시 사진에서는 NX가 작동하고 있어 스택에 직접 악성 코드(쉘코드)를 텍스트로 적어 넣고 그곳으로 점프해서 실행하는 해킹 방법 사용 불가능|
(이로인해 코드를 직접 주입하는 대신, 이미 프로그램 안에 존재하는 secret 함수나 ret 가젯의 주소로 점프하는 우회 방식을 실습에서 사용)

5. PIE: No PIE (0x400000)
의미: PIE(Position Independent Executable)는 프로그램이 실행될 때마다 메모리 주소를 랜덤하게 섞어버리는 방어 기법
-> 실습을 진행하며 compile과정에서 작동을 중지해놓았고 기준 주소가 0x400000으로 고정되어 있다고 명시적으로 알려줌
(PIE가 꺼져 있어 디버거(GDB)에서 찾은 secret 함수의 주소(0x401156)와 ret 가젯의 주소(0x40118f)가 실제 실행할 때도 바뀌지 않고 똑같이 유지되었으며, 만약 PIE가 작동했다면 주소가 매번 바뀌어 하드코딩된 주소로 공격 불가능)

6. SHSTK / IBT: Enabled
의미: Intel CET(Control-flow Enforcement Technology)라는 하드웨어 기반의 최신 보안 기술
SHSTK (Shadow Stack): CPU가 Return Address를 몰래 백업(그림자 스택)해두고, 우리가 덮어쓴 주소와 비교해서 다르면 중지
IBT: 비정상적인 Jump 감지

7. Stripped: No / Debuginfo: Yes
의미: 프로그램 내부의 함수 이름(vuln, secret 등)과 디버깅용 정보가 지워지지 않고 그대로 남아있다는 뜻으로 이로인해 gdb에서 disas vuln처럼 함수 이름만으로 쉽게 코드 분석 가능
