Challenge-1

1. malloc() 실패 시(반환값이 NULL) 어떻게 처리해야 하는지

컴퓨터의 물리적 메모리(RAM)가 가득 찼거나, 프로그램이 운영체제로부터 할당받을 수 있는 최대 힙 메모리 크기를 초과했을 때 malloc 함수는 메모리 할당에 실패한다. 이때 함수는 NULL 포인터를 반환하며, Segmentation Fault 에러를 발생할 수 있음. 따라서 malloc을 호출한 직후 컴파일러와 운영체제에게 메모리가 잘 할당되었는지 NULL체크를 하는 조건문을 작성하여 이러한 문제를 처리할 수 있음 (week07_challenge01 참조)

2. free() 하지 않으면 어떤 문제가 생기는지 (Memory Leak)

Heap 영역은 사용자가 제어하는 메모리 공간이기에 지역 변수가 저장되는 Stack 영역 처럼 함수가 끝나면 자동으로 파괴되지 않는다. 따라서 개발자가 명시적으로 free 함수를 호출하기 전까지는 프로그램이 켜져 있는 동안 메모리에 영원히 상주하게 됨
이렇게 free 하지 않은 채 함수가 종료되거나 포인터 변수에 다른 주소를 대입해 버리면, 할당된 메모리 공간은 힙 영역의 한 구석을 계속 차지하는 Memory Leak 현상이 발생. 이러한 현상은 단기적으로는 당장 문제를 일으키지 않는다 할지라도 장기적으로 메모리 점유율이 높아져 시스템 전체의 성능이 극도로 저하될 수 있음

Challenge-2

1. gdb 관찰 결과

free() 호출 전: 0x5555555592a0 주소에는 할당한 정수 값인 10의 16진수 형태인 0x0000000a 저장
free() 호출 후: 동일한 주소의 값이 0x55555559, 0x00000005, 0x34731455 와 같은 전혀 다른 16진수 값으로 변조

-> free() 함수는 메모리 값을 0으로 초기화하는 것이 아니며, 운영체제가 해당 메모리를 회수하며 다음 메모리 할당을 관리하기 위한 내부 기록을 우리가 쓰던 데이터 공간에 그대로 덮어쓰는 것

2. Dangling Pointer가 위험한 이유

Dangling Pointer란 메모리가 이미 운영체제에 반납되었음에도 불구하고, 여전히 그 공간의 메모리 주소를 가리키고 있는 포인터 변수

예측 불가능한 오작동: 프로그램은 이 포인터가 가리키는 곳에 여전히 유효한 10 이라는 데이터가 있다고 착각하지만 실제로는 gdb 결과처럼 시스템의 메타데이터가 들어있거나, 다른 프로세스에 의해 할당된 완전히 다른 데이터가 들어와있음

데이터 오염 및 크래시: 이 포인터를 통해 값을 읽으면 쓰레기 값을 연산에 사용하여 논리적 오류가 발생. 만약 이 해제된 공간에 새로운 값을 쓰려고 시도하면, 운영체제의 메모리 관리 구조 자체를 파괴하여 즉각적인 프로그램 크래시(Segmentation Fault)를 유발

3. Use After Free (UAF) 취약점과의 연결성

포인터 방치: 프로그램이 메모리를 free() 했지만, 포인터 변수 a 를 NULL 로 초기화하지 않아 Dangling Pointer 생성

재할당 유도: 공격자가 의도적으로 특정 입력을 가해 새로운 악성 데이터를 메모리에 할당하도록 유도하며, 이때 운영체제는 효율성을 위해 방금 해제된 주소(0x5555555592a0)를 공격자의 악성 데이터에게 재할당

제어권 탈취 (UAF 발생): 공격자가 심어둔 악성 데이터와 프로그램 내에 남아있던 Dangling Pointer는 완벽하게 동일한 물리적 주소를 공유하게 됨. 기존 프로그램이 정상적인 절차인 줄 알고 Dangling Pointer를 이용해 함수 포인터를 실행하거나 값을 읽는 순간, 공격자의 코드가 실행되거나 시스템 정보 유출 발생

Challenge-3

1. 힙 메타데이터와 장부

운영체제는 메모리가 free 될 때마다 그 공간들을 '단일 연결 리스트(Singly Linked List)' 형태의 장부로 묶어서 관리하며, 최신 리눅스에서는 이를 Tcache (Thread Local Cache) 또는 Fastbin 이라고 명칭

A 공간 해제 후 시스템은 A의 메타데이터 구역에 NULL 입력 (장부 상태: Head -> A -> NULL)

B를 해제하면, B의 메타데이터에 구역에는 A 입력 (장부 상태: Head -> B -> A -> NULL)

시스템은 이처럼 해제된 메모리 안에 Forward Pointer를 적어두는 방식으로 하나의 체인을 형성

2. Double Free 발생: Circular Link

첫 번째 free(A): Head -> A -> NULL
이후 free(A): Head -> A -> A -> A... (Circular Link 생성)

3. 메타데이터 변조: Tcache Poisoning

이후 공격자는 프로그램의 정상적인 기능을 이용해 malloc을 호출

시스템은 장부 맨 앞에 있는 A를 할당하지만 장부는 꼬여있기 때문에, 다음 빈 공간을 가리키는 Head는 여전히 A 를 가리킴

공격자는 할당받은 A 공간에 일반적인 데이터를 쓰는 척하면서, 메모리에 시스템의 핵심 관리자 주소(예: __free_hook 이나 스택의 반환 주소, 이하 0xTARGET)를 덮어 씌움

결국 A 안에 들어있던 메타데이터(다음 빈 공간 주소)가 해커의 데이터로 덮어씌워져 시스템의 빈 공간 장부는 Head -> A -> 0xTARGET 이라는 오염된 상태로 변경

4. 제어권 탈취 (Arbitrary Memory Allocation)

공격자는 두 번의 malloc 을 연속으로 호출

첫 번째 malloc: 시스템은 장부 맨 앞의 A를 할당해주며 Head 는 해커가 조작해 둔 0xTARGET 을 가리키게 됨

두 번째 malloc: 시스템은 0xTARGET을 공격자에게 일반 메모리인 것처럼 할당

마지막으로 공격자는 0xTARGET에 악성 쉘코드(Shellcode)의 주소를 적어 넣어 프로그램이 원래의 관리자 함수를 실행하려 할 때, 쉘코드가 대신 실행되게 만듬
